# 空白工程与创建流程规划

更新日期：2026-11-18。M5.1 至 M5.3 已实现，实际命令与使用方式见[创建工程与验证](project-scaffold.md)。本文保留设计与验收约定，实际实现以使用文档为准。

## 目标与职责

使用者选择工程名称、目标目录和技术栈后，完成“创建工程 → 接入规范 → 验证”，得到可以开始业务开发的独立项目。工具包维护可复用空白模板，业务代码和数据留在各自仓库。

| 层次 | 职责 | 当前状态 |
| --- | --- | --- |
| M2 用户级安装 | 部署完整工具包、规则和 Skills，维护更新、诊断与卸载 | 已实现，真实宿主加载待验收 |
| 空白工程模板 | 提供应用入口、基础配置、最小示例与可执行检查 | 已实现 |
| 工程创建编排 | 选择模板、预览冲突、生成应用、衔接规范和验证 | 已实现 |
| M3 项目规范初始化 | 按目录范围接入规范、采用配置与来源记录 | 已实现，不创建应用代码 |
| 工程验证 | 执行已生成的检查入口和跨端冒烟测试，保留实际结果 | 已实现 |
| M4 开发收尾 | 核对任务范围，按项目策略检查和本地提交；推送单独授权 | 已实现 |

创建、规范接入与验证分别报告结果。源码生成完成、检查通过、宿主规则加载通过是不同结论，不互相替代。业务项目仅保留采用的规范与创建来源，不复制整个工具包，也不把本工具包变成业务 Monorepo。

## 首批模板与选型

首批支持三个组合。优先打通 React + FastAPI，再复用相同前端完成独立前端和 React + NestJS；常规业务 API 与 Python 生态的选型边界仍以[规范库](../standards/README.md)为准，不改变既有后端选型约定。

| 模板标识 | 生成内容 | 规范映射 |
| --- | --- | --- |
| `react-fastapi` | `apps/web` 与 `apps/api` | `react-vite`、`fastapi` |
| `react-vite` | `apps/web` | `react-vite` |
| `react-nestjs` | `apps/web` 与 `apps/api` | `react-vite`、`nestjs-fastify` |

- 前端固定采用已有[React 规范](../standards/frontend/react-vite.md)：React、TypeScript、Vite、pnpm、Ant Design、UnoCSS、React Router、Zustand、Axios。Zustand 管理客户端状态，服务端查询缓存不默认引入 TanStack Query。
- Python 后端采用已有[FastAPI 规范](../standards/backend/fastapi.md)：FastAPI、Pydantic、uv，以及 Ruff、mypy、pytest 检查入口。
- TypeScript 后端采用已有[NestJS 与 Fastify 规范](../standards/backend/nestjs-fastify.md)：NestJS、Fastify adapter、TypeScript、pnpm，以及实际配置的格式、Lint、类型、测试与构建入口。
- 模板维护经过兼容验证的运行时、包管理器和依赖版本及锁文件。实施时核对官方兼容要求并记录验证环境，不在本规划中猜测版本，也不在用户创建时无条件追随 latest。
- 数据库、认证、Worker、Redis、对象存储、向量检索和模型供应商接入不预装进最小模板；按实际项目需求扩展。空白工程不包含业务案例、用户数据、固定账号或真实凭证。

前端使用 Vitest，NestJS 使用 Node.js 测试运行器与 Fastify 注入测试。最小工程应能在无数据库和外部模型服务的条件下启动与验收。

## 模板产物与目录

模板资产位于 `templates/projects/`，按 `shared/`、`react-vite/`、`fastapi/`、`nestjs-fastify/` 和组合清单组织。相同前端与公共配置只维护一份，由组合清单选择并声明变量、输出路径、技术栈映射及检查入口。

全栈工程生成以下结构；仅前端组合不生成 API 目录。目录仅在有实际文件和职责时创建。

```text
目标项目/
  README.md                       本项目启动、验证和扩展说明
  .gitignore                      依赖、构建产物与本地配置忽略规则
  AGENTS.md                       M3 管理的规范入口及项目原有约定
  .ai-dev-standards/               M3 管理的规范、采用配置和来源
  .ai-dev-scaffold/manifest.json   工程创建来源记录
  apps/
    web/                          前端入口、路由、请求层与最小页面
    api/                          后端入口、健康检查与最小接口测试
  scripts/                        本项目可独立运行的验证与冒烟入口
```

最低交付要求：

1. 前端包含应用壳、Ant Design 配置、UnoCSS 接入、React Router 首页与未匹配页面、错误恢复入口；用一个简单偏好展示 Zustand 的职责，不创建虚构业务模块。
2. 请求链为页面或 Hook → Service → Axios Client，具备超时、取消、错误归一化与返回数据校验。全栈组合通过真实健康检查接口展示加载、成功、失败和重试；前端单独组合不伪造后端可用结果。
3. 后端包含应用装配、配置读取、健康检查端点及契约测试；全栈组合的地址、开发代理和接口结构一致。仅为实际职责分层，不创建空 Repository 或万能 Service。
4. 提供无秘密值的配置示例、锁文件、真实检查入口与中文使用说明；所有手写模板代码遵循既有中文注释规范。简单环境默认本机可运行，不要求生产凭证。
5. 创建来源记录包含模板标识、工具包固定提交或发行版本、模板指纹和非敏感生成参数。业务源码交付后归项目所有，创建清单只用于追溯，不能作为未来自动覆盖业务修改的授权。

`.ai-dev-scaffold/` 与 M3 的受管规范目录分开，避免把应用源码误当作规范更新资源。运行日志和本机路径不写入共享采用配置；创建记录包含模板、输入参数、来源提交以及各输出文件的 SHA-256。

## 创建与验证流程

统一命令名为 `ai-dev-standards`。使用方式与参数见[创建工程与验证](project-scaffold.md)。

```text
ai-dev-standards create ./my-app --template react-fastapi
ai-dev-standards create ./my-app --template react-fastapi --apply --install --verify
ai-dev-standards verify --project ./my-app
```

流程约定：

1. **预览。** 检查目标目录、现有规则和 Git 状态，输出模板、拟创建文件、冲突、依赖安装与验证动作；默认不写入、不联网，也不执行包管理器。
2. **生成。** 显式应用后，按固定模板生成应用代码与配置，核对输出路径和内容。仅生成文件的模式保持可用。
3. **接入规范。** 模板组合提供真实目录范围和检查入口，调用 M3 生成 `AGENTS.md` 与 `.ai-dev-standards/`。规范正文仍只来自 `standards/`，创建器不维护第二套合并逻辑。
4. **安装依赖。** 仅在明确选择安装时执行，预览说明将联网及运行依赖安装过程；采用锁文件，不悄悄升级版本，不改用户的全局运行时或包管理器配置。离线或缺少工具时如实停止并给出继续步骤。
5. **验证。** 执行配置内真实命令，分别记录通过、失败、未运行与原因。全栈组合补充实际前后端连接的冒烟验证；失败时保留工程和日志，返回失败，不报告创建流程全部完成。
6. **交付与收尾。** 报告启动方式、采用版本和检查结果。创建器、验证器本身不自动提交；完整开发工作流确认完成后，复用 M4 按 local/manual 策略收尾，用户“不要提交”指令优先，推送仍单独授权。

新项目的 Git 初始化作为独立显式选项；已有仓库保留其历史、远程与暂存边界，不在工具包仓库内部创建嵌套业务仓库。独立 `verify` 入口不重新生成项目、不安装依赖、不提交，便于失败后修复和重复验证。

模板的规范映射与检查声明应作为同一份创建输入，生成 M3 配置后由验证器和 M4 复用，避免分别维护检查清单。生成的检查入口应在业务项目中可独立执行，不依赖维护者的绝对路径。

## 已有目录与失败边界

| 目标情况 | 行为 |
| --- | --- |
| 不存在的目录或空目录 | 默认创建模式；预览通过后显式应用 |
| 只有规划文档的目录或仓库 | 显式选择已有目录接入模式，先检查完整变更范围，再只新增确定无冲突的工程文件 |
| 已有应用代码 | 使用现有 M3 接入规范；首批创建器不自动合并或迁移技术栈 |
| 同名文件、无法确认的受管区块或越界链接 | 停止并报告具体冲突，不提供默认强制覆盖 |

规划型仓库须保留原 `README.md`、`docs/`、Git 历史、规则及已有修改。模板的启动说明可写入新的开发说明文件并报告其路径，不替换原 README；已有 `.gitignore`、`AGENTS.md` 等需按明确归属合并或报告冲突，不能一律覆盖。技术栈和目录先明确，再接入规范，不用根目录占位及空检查清单冒充完整初始化。

重复运行不能覆盖用户已经修改的应用源码；精确重复且内容一致时才允许无操作返回。受中断影响的文件记录阶段与本次创建范围，只有仍能确认归属的内容才允许清理或恢复；依赖安装、外部进程与文件写入不声称具有整体原子性。首次生成失败不得删除原目录或用户后续改动。

工具包更新、卸载及模板换版不自动改写已经生成的业务项目。业务规范升级与应用模板迁移是不同需求，均不混入首批创建流程。

## 分发与 M2 衔接

目标是在新电脑通过固定版本的发布产物或受支持安装入口取得完整工具包，不要求用户手动维护一份源码克隆；每个业务项目通过统一短命令创建或验证。

- 先验证本地完整副本和统一入口，再确定发布渠道。可执行安装命令、发布地址和版本标签只在产物实际可用后写入安装说明，不预先宣称 npm、PyPI 或其他渠道已发布。
- 安装入口复用 M2 的预览、归属、备份、诊断与恢复机制。选择仅在项目使用 CLI 时，不默认修改用户级规则；安装 Skills 和全局规则时明确列出资源。短命令入口若落盘，也要纳入可追溯的安装与卸载范围。
- M2 发布根据模板资产清单校验和打包，覆盖 TypeScript、TSX、CSS、HTML、点文件及锁文件等实际资源；继续排除依赖目录、构建缓存、真实环境配置和凭证。
- 下载采用固定版本与可校验产物，来源及校验失败时停止。更新不静默拉取浮动分支，不绕过 M2 的显式更新流程；模板许可证与第三方声明纳入发布检查。
- 安装副本必须包含完整模板和运行资源。删除原源码克隆后，仍能创建项目、接入规范、验证、诊断及卸载；不能只在开发仓库中证明命令可用。

## 验证与验收

验证分为工具包测试、生成项目测试与真实使用环境验收，分别记录，不将其中一层通过当作全部通过。

- 工具包测试：模板变量与路径检查、组合一致性、规范链接、中文说明、无凭证和本机路径；预览不写入、冲突拒绝、重复执行、失败中断及已有修改和暂存边界保留。原 M2 至 M4 自动化检查必须继续通过。
- 前端项目：实际执行格式、Lint、类型、测试与构建；验证路由、请求失败恢复及最小页面交互。检查脚本不能仅输出成功，不能把空测试集记为通过。
- FastAPI 项目：实际运行 Ruff、mypy、pytest，验证健康检查响应和契约。NestJS 项目：实际运行所配置的格式、Lint、类型、测试与构建，并通过 Fastify 注入测试验证 HTTP 边界。
- 全栈链路：使用隔离端口和合成数据启动实际服务，通过浏览器完成页面访问与真实 API 请求，验证成功及后端不可用时的恢复行为；超时、端口占用和子进程退出正确报告，清理仅涉及本次启动的进程。
- 安装与发布：从安装副本、无原克隆环境以及另一独立环境逐项验证三个组合；网络不可用、依赖安装失败和缺失运行时不误报成功。沿用首版 macOS 验收范围，其他系统单独列状态。
- 工作流验收：在一次性 Git 仓库完成创建、规范接入、验证和一个真实小修改，再使用 M4 核对提交范围与 SHA；新会话确认规则和两个既有 Skill 的加载，未授权时不推送。

验收记录列出工具包提交、模板标识、依赖与运行时版本、实际命令及退出码、未执行项和原因。仅在有全部必要证据时将对应模板标记为可用。

## 实施顺序与完成标准

前三阶段已交付，维护者已完成本机验收。M5.4 的第二台电脑验收与正式发布仍待完成。

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| M5.1 空白模板资产 | 共用基础配置、React 前端、FastAPI 与 NestJS 后端、组合清单 | 先人工展开 React + FastAPI 并跑通启动与检查，再逐项验收其余两个组合；明确兼容版本、锁文件与中文说明 |
| M5.2 创建与验证编排 | 模板生成、M3 衔接、独立验证入口、已有规划目录模式及恢复记录 | 在隔离目录完成默认预览、显式应用与全部必要检查，覆盖冲突、失败及重试；M4 可接续收尾 |
| M5.3 便捷命令分发 | 固定版本获取方式、统一短命令、M2 模板打包与入口生命周期 | 无需手动克隆源码即可安装与调用，删除原克隆后完整链路仍可用，更新和卸载不影响业务项目 |
| M5.4 独立环境与发布 | 用户使用文档、模板验收矩阵、许可证、正式产物与标签 | 本机新会话和另一独立环境完成全流程，明确支持范围及未完成项；发布与推送按单独授权执行 |

实施进度：

- [x] 明确模板变量、组合清单、输出文件归属与首批兼容版本。
- [x] 实现共用 React 前端和 FastAPI 后端，先跑通真实健康检查链路。
- [x] 复用前端产物验收独立前端组合，再实现 NestJS 后端组合。
- [x] 实现创建预览与安全写入，复用 M3 并补齐依赖安装、验证和失败继续路径。
- [x] 将完整模板与命令入口接入 M2，完成无原克隆的隔离测试。
- [x] 支持构建固定提交的单文件发行包。
- [x] 完成本机验收。
- [ ] 完成第二台电脑验收，确认许可证与正式发布范围。见[发布确认稿](release-scope.md)。

本规划不包含业务功能开发、参考项目源码打包、已有应用的自动技术栈迁移、业务规范升级或规范提取 Skill。上述原有待办继续独立记录。

实际执行环境和完整结果见[M5 验证记录](verification/m5-scaffold.md)。
