# 首发后的优化规划

`v0.1.0` 已通过 GitHub Release 发布，可下载固定版本的 `.pyz` 和 `.sha256`，无需克隆源码。第一阶段的手动验收已在 GitHub 运行通过，后续增加的 `main` 自动发布待首次远端验收。后两阶段按顺序实施、各自验收，再按实际改动安排版本。[首次托管验收](https://github.com/chengit16/ai-dev-standards/actions/runs/44258864424) · [发版指南](github-release.md) · [发行包用法](project-scaffold.md#使用固定版本的发行文件)

| 顺序 | 交付内容 | 完成后可以怎么用 |
| --- | --- | --- |
| 1 | GitHub Actions 构建、验收及发布发行包 | 推送 `main` 后自动验收和发布，手动运行也可单独验收候选包。 |
| 2 | 固定版本的下载、校验与安装入口 | 在新电脑按版本获取工具包，先预览，再确认安装或升级。 |
| 3 | 用一个真实项目试用 Cursor | 根据实际任务判断哪些项目规则和 Skills 可以复用，以及是否需要适配。 |

## 第一阶段　自动构建并验收发行包

新增手动触发的 GitHub Actions 工作流，以完整 Git 提交号选定候选版本。检出该提交、运行仓库现有自动化测试，并复用 `release --ref … --output …` 构建。通过验证后，将同一次构建的 `.pyz` 与 `.sha256` 上传为工作流附件，记录对应提交、校验结果和安装演练结果。

### 验收标准

1. 检出的提交、运行测试的代码、构建来源以及包内 `_toolkit-source.json` 记录一致，包内含 MIT 许可和已确认署名，`.sha256` 校验通过。
2. 使用隔离的 `--home` 分别验证全新安装和从上一公开版本升级。首次验收用 `v0.1.0` 作为升级起点。两条路径都运行 `doctor` 并验证可卸载，升级及卸载后核对测试预置的用户配置仍在。
3. 测试、校验或演练失败时，工作流标记失败，日志能定位故障步骤，供发布使用的附件只在全部检查通过后上传。
4. 维护者能下载这对附件，复核校验和与目标提交。`doctor` 的结果记录为部署检查，规则与 Skills 的实际读取另外在宿主会话中验收。

验收作业使用仓库只读权限。维护者在推送 `main` 前确认公开范围；推送触发的发布作业在验收通过后上传并核对草稿附件，为候选提交打标签，再公开 GitHub Release。手动运行继续提供候选包供复核。[公开范围](release-scope.md) · [自动发布流程](github-release.md#推送-main-后自动发布)

## 第二阶段　简化固定版本安装和升级

提供按明确版本号从 GitHub Release 下载发行包及校验文件的命令入口。校验通过后，复用现有 `install` 或 `update` 预览，确认后再用 `--apply` 应用。保留源码和已下载发行包的使用方式，支持离线操作。新增 `--version` 用于查看当前执行的工具包版本和来源提交，源码或本地构建没有可确认的发布版本时显示来源信息。

### 验收标准

1. 新电脑可以直接使用文档里的命令，按指定版本下载、校验、预览、安装并运行 `doctor`。已有安装也能指定目标版本并显式升级。
2. 预览展示本机目标路径和计划变更。同版本重复执行复用现有幂等行为，发生可恢复的写入失败时沿用现有回滚和中断恢复流程。
3. 版本不存在、网络失败、附件缺失和校验不一致都有明确错误，受管配置在这些下载或校验失败时保持原状。
4. 版本查询可区分不同发行包，升级后用已安装入口能查看实际来源版本。业务项目自行控制已采用的规则版本，项目规则通过 `upgrade-rules` 单独预览和升级。

完成后，在安装说明补齐新装、升级、离线使用和排查示例。[安装与本机验收](installation.md) · [升级项目规则](project-bootstrap.md#升级已接入项目的规范)

## 第三阶段　用真实项目验证 Cursor

选一个已经接入规范的 React + FastAPI 项目，在独立分支上完成一项小改动。先在新会话观察项目 `AGENTS.md` 和引用的前后端规范是否被实际采用，再检查实际改动、项目检查结果和本地收尾结果。

### 验收标准

1. 记录 Cursor 版本、会话入口、工作目录、任务范围、实际读取的规则和实际运行的检查。以改动和检查日志作为遵循规则的证据。
2. 分别验证 `extract-standards`、`project-bootstrap`、`finish-task` 的使用方式，记录能否发现、调用并完成预期步骤。涉及提取或初始化的验证使用授权的项目副本，提交验证仅使用本地分支。
3. 只有实际验证发现差异时才提出适配，优先复用现有规则和 CLI，并用同一任务重试。共享仓库只记录可公开的方法和结论，验证结果限定在已测工具版本、项目栈和流程。
