# AI 开发规范工具包项目规划

创建日期：2026-11-16。状态：规划和第一版规范已建立，自动化待实现。

## 一、背景与目标

每次使用 AI 开发新项目，在技术框架确定之后，都需要重复要求 AI 参考已有项目的前后端代码规范、生成当前项目规范，并交代开发完成后的 Git 提交要求。

本项目将这些重复操作整理为可安装、可版本化、可跨电脑复用的工具包。使用者一次维护个人偏好和参考规范，每台电脑安装一次，每个业务项目初始化一次，日常任务按既定流程执行。

核心目标：

1. 用独立 Git 仓库集中维护规则、Skills、模板和安装工具。
2. 从参考项目提取可复用规范，并按技术栈组合。
3. 在技术栈确定后，为业务项目生成适用的规则和检查配置。
4. 将任务完成后的检查与提交纳入固定工作流。
5. 支持另一台电脑克隆、安装、更新与卸载。
6. 使规则来源、版本和项目差异可追溯。

## 二、第一版范围

第一版支持 Codex，优先验证 macOS 上的完整流程。其他操作系统的兼容性在完成对应验证前不作承诺；路径和文件操作设计应避免不必要的平台绑定。

包含：

- 一套全局规则及可管理的安装区块。
- 通用规范，以及使用者选定的一套前端和两套可独立选用的后端技术栈规范。
- 规范提取、项目初始化、任务收尾三个工作流。
- 安装、更新、诊断和卸载工具。
- 版本记录、本机配置分离及基本验证。

后续范围：其他 AI 开发工具适配、更多技术栈、Windows/Linux 验证、插件打包和可视化配置。

当前已交付仓库骨架、规划文档和可手动选用的[第一版开发规范](../standards/README.md)，尚未安装或修改使用者的全局规则与 Skills。

## 三、整体结构

| 层次 | 存放位置 | 责任 |
| --- | --- | --- |
| 全局行为入口 | `rules/` | 通用偏好、初始化触发条件、任务收尾要求 |
| 规范资产 | `standards/common/`、`standards/frontend/`、`standards/backend/` | 按职责和技术栈组织规范及示例 |
| 可复用流程 | `skills/` | 提取规范、生成项目规则、检查并提交 |
| 项目生成内容 | `templates/` | 项目规则入口、详细规范和检查配置模板 |
| 生命周期工具 | `scripts/` | 安装、更新、诊断、卸载与恢复 |
| 版本说明 | `versions/` | 兼容策略和迁移说明 |

仓库根目录的 `AGENTS.md` 仅用于维护工具包自身。安装内容有独立来源，避免将维护流程误装到业务项目中。

## 四、规范来源与技术栈组合

参考项目仅需在提取或主动更新规范时可访问。使用已提取规范的其他电脑不必拥有原参考项目。

提取流程：

1. 检查参考项目明确的规范、配置和代表性实现。
2. 区分明确要求、由代码推断的惯例，以及需要进一步确认的选择。
3. 提取命名、目录、组件职责、请求处理、异常、日志、数据访问和验证方式等规则。
4. 排除业务专属逻辑、历史兼容负担、凭证和不适合跨项目分发的内容。
5. 记录参考来源、可确定的提交版本、适用技术栈和提取日期。
6. 用简洁示例说明规则，整理为可组合的规范资产。

通用规范、前端规范和后端规范分别维护。首版的适用范围、组合方式与各套规范见[规范库](../standards/README.md)。

没有匹配规范时，说明缺口并获取一次必要信息，不虚构已有规则。已有项目优先保留有效约定，补齐缺失部分；存在冲突时记录取舍，不盲目覆盖。

## 五、项目初始化工作流

工作流名称暂定为 `project-bootstrap`。

触发条件：技术栈已确定，使用者已要求开展开发，且项目尚未完成规范初始化。纯讨论技术选型时不提前写入业务仓库。

主要步骤：

1. 识别实际技术栈、现有项目说明、目录和工具配置。
2. 选取匹配的规范版本，检查是否存在项目级覆盖要求。
3. 生成或合并根目录 `AGENTS.md`，提供明确的规范读取入口。
4. 生成必要的通用、前端、后端规范和检查配置。
5. 记录工具包版本、规范组合、来源以及项目差异。
6. 验证文档引用和实际检查命令，报告生成结果。

项目根规则入口应保持简短，明确修改哪类文件前读取哪些规范，以及完成后执行哪些检查。不能仅生成大量文档而没有读取入口。

初始化须可重复执行：已有内容未变化时不重复追加；用户维护的内容和工具生成的内容应有清楚边界。

生成内容提交到业务项目仓库，并使用仓库内相对引用。基础开发规范不应依赖某台电脑上的工具包绝对路径；自动化工作流仍需对应 Skill 已安装。

## 六、任务完成与 Git 策略

工作流名称暂定为 `finish-task`。

“完成”定义为一个可独立验收的功能、修复或完整修改已交付，且项目要求的必要检查已通过。纯方案讨论、开发中间状态、无实际变更或检查失败，不触发完成提交。

| 策略 | 行为 |
| --- | --- |
| 手动 | 生成提交说明，按用户后续指令提交 |
| 自动提交 | 检查通过后自动本地提交；个人默认值 |
| 自动提交并推送 | 提交后向明确的远程和目标分支推送 |

配置只表达策略，不替代当前明确指令或运行环境权限。用户临时要求“本次不提交”或“不要推送”时，应遵循该要求。

收尾规则：

- 以实际 diff 为依据，只纳入本任务改动，保留用户原有修改和部分暂存边界。
- 没有实际变更时不制造空提交。
- 检查失败时不提交成功结论，不绕过 hook。
- 提交标题采用 `<type>: <中文摘要>`，正文为必要的中文修改列表。
- 不因包含样式文件就把行为变化误标为纯格式修改。
- 提交后核实 SHA、提交范围和剩余工作区变更。
- 提交成功而推送失败时保留本地提交，重试推送不重复创建提交。
- 推送前确认目标与待推送历史；目标不明确、存在冲突或历史分叉时不猜测处理。

示例：

```text
feat: 新增订单筛选功能

- 支持按订单状态和创建时间筛选
- 切换分页时保留当前筛选条件
```

现有 `git-commit-message` Skill 可作为迁移基础。它目前的“普通开发任务不自动提交”和“直接调用默认包含推送”需要与新策略统一，避免同时维护相互冲突的入口。迁移时保留有价值的范围核对和提交信息规则，不直接改写使用者现有文件。

## 七、安装、更新与卸载

安装计划使用用户级 Skill 发现目录，并为全局 `AGENTS.md` 管理独立区块。默认 Codex 路径及配置覆盖应在实现时根据实际环境检测，不能写死维护者用户名。

安装器要求：

- 检测现有全局规则、覆盖文件、同名 Skill 和安装状态。若覆盖文件导致安装规则未生效，应明确报告。
- 仅写入本工具包拥有的区块和文件；同名但不属于本工具包的内容不得静默覆盖。
- 修改前保存可恢复备份，记录安装版本、目标路径和拥有的文件。
- 重复安装不重复追加、不制造多套同名 Skill。
- 执行中断后可诊断并恢复，不把未完成状态报告为安装成功。

更新器要求：更新版本前检查已有安装状态，展示或记录差异，保留本机配置和用户自定义内容。

诊断器要求：检查规则是否处于有效加载位置、Skill 是否存在、安装记录与文件是否一致，并区分“文件已部署”和“已在新会话验证加载”。

卸载器要求：只移除仍可确认属于本工具包的内容；遇到安装后被用户修改的文件时保留或提示处理，不恢复过时备份覆盖后续修改。

第一版无需发布到包管理器，可先通过克隆仓库和执行安装入口使用。脚本实现与验证完成之前，不提供看似可执行的安装命令。

## 八、本机配置与版本策略

可共享内容进入 Git；本机配置放入已忽略的 `local/` 目录，具体格式在实现阶段确定。绝对路径、私有参考仓库位置和机器差异不能成为公共规范的隐式依赖。

工具包采用 Git 标签发布版本。业务项目记录初始化时采用的工具包和规范版本，不随工具包更新自动改写。

规范升级应比较旧生成结果、当前项目内容和新模板，保留项目定制；出现冲突时呈现差异供处理，不整文件覆盖。第一版可先做到显式升级与差异预览，复杂自动合并逐步补充。

新电脑应能从已提交的规范和模板完成安装。选择固定发布标签有利于多台电脑使用一致版本。

## 九、可执行检查与能力边界

格式、类型、静态检查、提交格式等可量化要求由相应工具验证。架构职责和业务语义等要求仍需要规范指导与审查。

`AGENTS.md` 和 Skill 是模型指令，不是绝对执行保证。Git hooks 和 CI 可验证部分质量要求，不能独立判断需求是否完成，也不会代替开发工作流自动触发提交。

自动匹配 Skill 的准确性需验证，因此全局规则应明确何时调用初始化与收尾流程，并提供手动调用入口作为补充。

## 十、实施里程碑与验收标准

| 阶段 | 交付 | 验收标准 |
| --- | --- | --- |
| M0 项目建立 | 独立仓库、规划、维护规则和目录骨架 | 文档可访问、链接有效、当前状态明确 |
| M1 规范基础 | 通用规则、一套前端规范、两套后端规范、配置约定 | 来源可追溯，技术栈可组合，本机路径不进入共享规则 |
| M2 安装闭环 | 安装、诊断、更新和卸载入口 | 在隔离目录通过首次安装、重复安装、冲突、失败恢复和卸载验证 |
| M3 项目初始化 | 初始化 Skill 和模板 | 示例项目可生成有效规则，重复运行无重复内容，已有约定被保留 |
| M4 开发收尾 | 收尾 Skill 与提交策略 | 临时 Git 仓库验证正常提交、无变更、检查失败及已有修改场景 |
| M5 首次发布 | 使用文档、版本标签、迁移说明 | 另一独立环境按文档安装，完成示例项目初始化与提交 |

推送策略使用临时本地远程仓库验证目标分支与失败处理，不以真实业务远程仓库作为测试目标。

## 十一、待补充信息
