# AI 开发规范工具包项目规划

创建日期：2026-11-16。状态：M0 至 M4 已交付源码及隔离验证；M5 已交付空白工程模板、创建与验证流程及固定提交发行包，维护者已确认两台电脑验收通过。规范提取 Skill 和项目规范显式升级已实现。首发授权和公开范围已确认。

## 一、背景与目标

每次使用 AI 开发新项目，在技术框架确定之后，都需要重复要求 AI 参考已有项目的前后端代码规范、生成当前项目规范，并交代开发完成后的 Git 提交要求。

本项目将这些重复操作整理为可安装、可版本化、可跨电脑复用的工具包。使用者一次维护个人偏好和参考规范，每台电脑安装一次，每个业务项目初始化一次，日常任务按既定流程执行。

核心目标：

1. 用独立 Git 仓库集中维护规则、Skills、模板和安装工具。
2. 从参考项目提取可复用规范，并按技术栈组合。
3. 在技术栈确定后，为业务项目生成适用的规则和检查配置。
4. 将任务完成后的检查与提交纳入固定工作流。
5. 支持另一台电脑克隆、安装、更新与卸载。
6. 使规则来源、版本和项目差异可追溯。
7. 在同一工具包中维护可复用空白工程模板，串联“创建工程 → 接入规范 → 验证”，生成的业务代码由独立业务仓库维护。

## 二、第一版范围

第一版支持 Codex，优先验证 macOS 上的完整流程。其他操作系统的兼容性在完成对应验证前不作承诺；路径和文件操作设计应避免不必要的平台绑定。

包含：

- 一套全局规则及可管理的安装区块。
- 通用规范，以及使用者选定的一套前端和两套可独立选用的后端技术栈规范。
- 规范提取、项目初始化、任务收尾三个工作流。
- 安装、更新、诊断和卸载工具。
- 版本记录、本机配置分离及基本验证。
- M5 新增规划：空白工程模板、工程创建与规范接入编排、真实项目验证和免手动克隆的命令分发入口。使用方式见[创建工程与验证](project-scaffold.md)。

后续范围：其他 AI 开发工具适配、更多技术栈、Windows/Linux 验证、插件打包和可视化配置。

当前已交付仓库骨架、规划文档、[第一版开发规范](../standards/README.md)、[项目初始化](project-bootstrap.md)和[开发收尾](finish-task.md)。按用户安排先完成 M3、M4，现已补齐 [M2 安装闭环](installation.md)，维护者已完成两台电脑的安装验收。

空白工程的模板范围、命令草案、冲突边界和实施检查清单统一维护在[空白工程与创建流程规划](project-scaffold-plan.md)。本文件保留总体目标和里程碑，其他入口引用该规划，不复制完整设计。

## 三、整体结构

| 层次 | 存放位置 | 责任 |
| --- | --- | --- |
| 全局行为入口 | `rules/` | 通用偏好、初始化触发条件、任务收尾要求 |
| 规范资产 | `standards/common/`、`standards/frontend/`、`standards/backend/` | 按职责和技术栈组织规范及示例 |
| 可复用流程 | `skills/` | 提取规范、生成项目规则、检查并提交 |
| 项目生成内容 | `templates/` | 项目规则入口、详细规范和检查配置模板 |
| 空白工程模板 | `templates/projects/` | 可组合的前端、后端与公共基础配置 |
| 执行工具 | `scripts/` | 项目初始化、开发收尾、安装生命周期与恢复 |
| 版本说明 | `versions/` | 兼容策略和迁移说明 |

仓库根目录的 `AGENTS.md` 仅用于维护工具包自身。安装内容有独立来源，避免将维护流程误装到业务项目中。

业务项目不放入本工具包仓库。创建器从模板生成独立项目，再调用 M3 接入规范；模板不嵌入另一份规范正文，也不包含参考业务项目的源码、数据或凭证。

## 四、规范来源与技术栈组合

参考项目仅需在提取或主动更新规范时可访问。使用已提取规范的其他电脑不必拥有原参考项目。

提取由 [extract-standards Skill](../skills/extract-standards/SKILL.md) 执行，按以下步骤形成可审阅的规范。

1. 检查参考项目明确的规范、配置和代表性实现。
2. 区分明确要求、由代码推断的惯例，以及需要进一步确认的选择。
3. 提取命名、目录、组件职责、请求处理、异常、日志、数据访问和验证方式等规则。
4. 排除业务专属逻辑、历史兼容负担、凭证和不适合跨项目分发的内容。
5. 记录参考来源、可确定的提交版本、适用技术栈和提取日期。
6. 用简洁示例说明规则，整理为可组合的规范资产。

通用规范、前端规范和后端规范分别维护。首版的适用范围、组合方式与各套规范见[规范库](../standards/README.md)。

没有匹配规范时，说明缺口并获取一次必要信息，不虚构已有规则。已有项目优先保留有效约定，补齐缺失部分；存在冲突时记录取舍，不盲目覆盖。

## 五、项目初始化工作流

工作流为 [project-bootstrap Skill](../skills/project-bootstrap/SKILL.md)，配合 Python 标准库生成器与入口模板使用。完整工具包副本可直接运行，不依赖 M2 用户级安装；首次初始化使用 bootstrap，后续通过 [upgrade-rules](project-bootstrap.md#升级已接入项目的规范) 预览并应用。

触发条件：技术栈已确定，使用者已要求开展开发，且项目尚未完成规范初始化。纯讨论技术选型时不提前写入业务仓库。

主要步骤：

1. 识别实际技术栈、现有项目说明、目录和工具配置。
2. 选取匹配的规范版本，检查是否存在项目级覆盖要求。
3. 生成或合并根目录 `AGENTS.md`，提供明确的规范读取入口。
4. 复制选定规范及其本地链接依赖，生成采用配置、检查清单和受管入口；不自动创建项目尚未具备的 Lint、测试工具或依赖。
5. 记录工具包版本、规范组合、来源以及项目差异。
6. 验证文档引用和实际检查命令，报告生成结果。

项目根规则入口应保持简短，明确修改哪类文件前读取哪些规范，以及完成后执行哪些检查。不能仅生成大量文档而没有读取入口。

初始化须可重复执行：已有内容未变化时不重复追加；用户维护的内容和工具生成的内容应有清楚边界。

当前生成器在受管文件被改动、来源或配置变化及覆盖入口等冲突下停止，保留现场；不执行隐式升级。来源以内容集合指纹和 Git 提交追溯，项目差异与检查参数保存在仓库内。隔离测试覆盖生成、重复执行、原内容及暂存区保留、冲突和失败回滚；真实 Skill 发现与新会话加载留待用户安装验收，文件部署与诊断由 M2 提供。

生成内容提交到业务项目仓库，并使用仓库内相对引用。基础开发规范不应依赖某台电脑上的工具包绝对路径；自动化工作流仍需对应 Skill 已安装。

### M5 新建工程衔接

新建工程先确定模板与目录，创建最小可运行代码及真实检查入口，再由 M3 生成规范采用配置，最后执行检查和跨端冒烟验证。已有业务项目继续使用 M3 接入规范，不以空白模板覆盖已有实现；仅有规划文档的仓库采用显式的保留内容接入模式。完整范围见[空白工程规划](project-scaffold-plan.md)。

创建器与验证器不重复实现 M2 安装归属、M3 规范生成或 M4 提交逻辑。单纯生成文件不能报告工程已验证，未实现的组合或未执行的检查必须明确标记。

## 六、任务完成与 Git 策略

已实现 [finish-task Skill](../skills/finish-task/SKILL.md) 和收尾 CLI，操作方式与边界见[开发收尾使用说明](finish-task.md)。默认预览明确文件范围，执行时运行真实检查并按 local/manual 策略提交；推送使用独立子命令，默认不推送。

“完成”定义为一个可独立验收的功能、修复或完整修改已交付，且项目要求的必要检查已通过。纯方案讨论、开发中间状态、无实际变更或检查失败，不触发完成提交。

| 策略 | 行为 |
| --- | --- |
| 手动 | 生成提交说明，按用户后续指令提交 |
| 自动提交 | 检查通过后自动本地提交；个人默认值 |
| 自动提交并推送 | 提交后向明确的远程和目标分支推送 |

配置只表达策略，不替代当前明确指令或运行环境权限。用户临时要求“本次不提交”或“不要推送”时，应遵循该要求。

收尾规则：

- 以实际 diff 为依据，只纳入本任务改动，保留用户原有修改和部分暂存边界。
- 没有实际变更时不制造空提交。
- 检查失败时不提交成功结论，不绕过 hook。
- 提交标题采用 `<type>: <中文摘要>`，正文为必要的中文修改列表。
- 不因包含样式文件就把行为变化误标为纯格式修改。
- 提交后核实 SHA、提交范围和剩余工作区变更。
- 提交成功而推送失败时保留本地提交，重试推送不重复创建提交。
- 推送前确认目标与待推送历史；目标不明确、存在冲突或历史分叉时不猜测处理。

示例：

```text
feat: 新增订单筛选功能

- 支持按订单状态和创建时间筛选
- 切换分页时保留当前筛选条件
```

M4 已吸收现有 `git-commit-message` Skill 的范围核对、中文信息及失败重试规则。新入口按项目 local/manual 策略收尾，直接调用不附带推送授权；未改写旧的用户级 Skill。M2 已检测旧入口并要求明确保留选择，全局规则明确默认收尾路由；没有自动改写、删除或禁用旧 Skill。

临时索引仅导入已审核的任务文件，成功后同步对应真实索引项，保留其他暂存和工作区。index 模式支持同文件部分暂存；worktree 模式拒绝部分暂存，混合改动的补丁归属仍由 Skill 核实，不能自动猜测。检查发生在真实工作区，不能据此声称候选提交在干净快照中独立通过。Git 目录保留恢复记录；中断恢复当前需人工核查。隔离测试使用临时仓库与本地 bare 远程验证提交、失败、边界保留及推送重试，宿主加载留待最后安装验收。

## 七、安装、更新与卸载

已实现 `scripts/toolkit.py`，提供 install、doctor、update、uninstall、recover 子命令；默认预览，显式 --apply 才写入。采用用户级 Skill 发现目录，并为全局 `AGENTS.md` 管理独立区块。使用实际 HOME、CODEX_HOME 或显式隔离布局，不写死维护者用户名。用法见[安装与验收说明](installation.md)。

完整工具包副本保留相对资源结构，各 Skill 通过链接发现。安装只管理清单内资源和全局标记区块；前后快照、进程锁及事务日志支持失败回滚和显式恢复。doctor 区分部署一致、冲突、中断及尚未验证的宿主加载。以下约束已纳入实现与隔离验证，复杂系统故障仍按操作文档保留现场。

安装器要求：

- 检测现有全局规则、覆盖文件、同名 Skill 和安装状态。若覆盖文件导致安装规则未生效，应明确报告。
- 仅写入本工具包拥有的区块和文件；同名但不属于本工具包的内容不得静默覆盖。
- 修改前保存可恢复备份，记录安装版本、目标路径和拥有的文件。
- 重复安装不重复追加、不制造多套同名 Skill。
- 执行中断后可诊断并恢复，不把未完成状态报告为安装成功。

更新器要求：更新版本前检查已有安装状态，展示或记录差异，保留本机配置和用户自定义内容。

诊断器要求：检查规则是否处于有效加载位置、Skill 是否存在、安装记录与文件是否一致，并区分“文件已部署”和“已在新会话验证加载”。

卸载器要求：只移除仍可确认属于本工具包的内容；遇到安装后被用户修改的文件时保留或提示处理，不恢复过时备份覆盖后续修改。

可通过完整源码或固定提交的单文件发行包使用。用户级安装和更新也可指定 GitHub 正式版本，自动下载并校验发行包。业务项目规范继续通过单独的 `upgrade-rules` 更新。[安装方式](installation.md#按版本安装和升级) · [创建工程与验证](project-scaffold.md) · [发布范围](release-scope.md)

## 八、本机配置与版本策略

可共享内容进入 Git；本机配置放入已忽略的 `local/` 目录，具体格式在实现阶段确定。绝对路径、私有参考仓库位置和机器差异不能成为公共规范的隐式依赖。

工具包采用 Git 标签发布版本。业务项目记录初始化时采用的工具包和规范版本，不随工具包更新自动改写。

已提供显式规范升级。正常升级保留项目采用配置与区块外规则，更新前展示差异。受管内容有手工修改时，先由维护者整理差异。自动三方合并留待后续评估。

新电脑应能从已提交的规范和模板完成安装。选择固定发布标签有利于多台电脑使用一致版本。

## 九、可执行检查与能力边界

格式、类型、静态检查、提交格式等可量化要求由相应工具验证。架构职责和业务语义等要求仍需要规范指导与审查。

`AGENTS.md` 和 Skill 是模型指令，不是绝对执行保证。Git hooks 和 CI 可验证部分质量要求，不能独立判断需求是否完成，也不会代替开发工作流自动触发提交。

自动匹配 Skill 的准确性需验证，因此全局规则应明确何时调用初始化与收尾流程，并提供手动调用入口作为补充。

## 十、实施里程碑与验收标准

| 阶段 | 交付 | 验收标准 |
| --- | --- | --- |
| M0 项目建立 | 独立仓库、规划、维护规则和目录骨架 | 文档可访问、链接有效、当前状态明确 |
| M1 规范基础 | 通用规则、一套前端规范、两套后端规范、配置约定 | 来源可追溯，技术栈可组合，本机路径不进入共享规则 |
| M2 安装闭环 | 安装、诊断、更新和卸载入口 | 在隔离目录通过首次安装、重复安装、冲突、失败恢复和卸载验证 |
| M3 项目初始化 | 初始化 Skill 和模板 | 示例项目可生成有效规则，重复运行无重复内容，已有约定被保留 |
| M4 开发收尾 | 收尾 Skill 与提交策略 | 临时 Git 仓库验证正常提交、无变更、检查失败及已有修改场景 |
| M5 首次发布（扩展规划） | 空白工程模板、创建与验证编排、便捷命令分发、使用文档与版本标签 | 在独立环境从固定版本安装，完成创建工程、规范接入、真实验证与收尾提交；原 M2 至 M4 能力无回归 |

M5 按 M5.1 模板资产、M5.2 创建与验证编排、M5.3 命令分发、M5.4 独立环境与发布依次交付。先完成 React + FastAPI 的完整链路，再验收独立前端和 React + NestJS 组合；具体完成标准以[分阶段计划](project-scaffold-plan.md#实施顺序与完成标准)为准。原有本机安装验收可先行，不因新增范围而被标记为已通过。

推送策略使用临时本地远程仓库验证目标分支与失败处理，不以真实业务远程仓库作为测试目标。

首发后的实施顺序和验收标准见[首发后的优化规划](next-steps-plan.md)。
