# 初始化项目开发规范

## 定位与范围

本 Skill 随完整 ai-dev-standards 工具包使用。若入口为符号链接，先解析本文件的真实路径；工具包根目录是实际所在目录的上两级，执行前验证其中有 `standards/README.md` 和 `scripts/project_bootstrap.py`。单独拷贝本目录不能获得生成器和规范，缺少资源时先定位用户的工具包副本，不猜测绝对路径或自动安装。

读取[规范选择入口](../../standards/README.md)，需要操作说明时读取[初始化使用说明](../../docs/project-bootstrap.md)。生成器依赖 Python 3.11+ 和 Git，只操作用户指定的项目；不改用户级配置，不运行项目命令、不提交或推送。完成后的检查与本地提交仍按目标项目的授权和约定执行。

## 识别并形成采用配置

- 先读取目标项目及适用父目录、子目录的规则和 README。若存在 `.codegraph/`，代码定位优先使用 CodeGraph；否则查实际配置与代码。查看 Git 工作区及暂存边界，避免本次生成夹带已有工作。
- 从 package.json、工作区配置、pyproject.toml、已有检查脚本与代表性代码核实技术栈和对应目录。新项目按已确认的计划选择；现有 React 项目不因缺少 Ant Design、Axios 等就自动安装或改造，明确记录既有差异。
- 只选择实际适用的 `react-vite`、`nestjs-fastify`、`fastapi`。不匹配的技术栈说明缺口，先保留既有规则。多个后端只有实际存在并有明确目录时一起选择，不因规范库有两套就默认全启用。
- 读取选中规范，与已有规则比较。把格式、请求层、测试工具、架构等有效差异写入 `deviations`，说明以哪份已有约定为准；不能只写“沿用原规则”掩盖已知冲突。无法自行确定的实质冲突才询问用户。
- 以[配置示例](../../templates/project-bootstrap/config.example.json)为结构，填写栈到目录的映射、实际存在的检查命令参数数组与工作目录，以及 `local` 或 `manual` 提交策略。检查只登记可确认的项目入口，缺失项明确报告；仅有测试库依赖不等于存在可用测试命令。
- 项目根有非空 `AGENTS.override.md` 时，说明普通 AGENTS 入口可能被遮蔽，先按项目约定解决有效入口，不删除覆盖文件。子目录规则优先级与加载字节限制也要在验收中检查。

## 生成并验证

在工具包根目录执行 `python3 scripts/project_bootstrap.py --project <目标目录> --config <配置文件>` 预览。配置先放在仓库外的临时文件中；共享内容只写相对路径，不含凭证、私有业务内容或本机路径。

核对文件清单和 AGENTS 区块差异。用户已授权初始化或技术栈已定且要求开展开发时，直接追加 `--apply` 应用；仅请求预览则保持只读。

生成后检查仓库相对链接、实际目录映射、配置与来源清单，再用生成的 `.ai-dev-standards/project.json` 重复预览，结果应为无需写入。按目标项目要求执行适用验证，报告实际结果；脚本输出“未执行检查”不能替代运行检查。

已有项目要采用新规范或采用配置时，走独立的 [upgrade-rules 流程](../../docs/project-bootstrap.md#升级已接入项目的规范)。先预览差异。受管内容已改动、已有同名文件或中断锁时，保留现场并按文档整理差异或恢复。

交付说明给出生成文件、选定组合、保留的差异、来源指纹、已执行检查及未完成项。仅生成文档不代表已安装 Skill 或已在新会话加载；由用户后续统一进行本机安装验收。
