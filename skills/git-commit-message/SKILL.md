# 中文 Git 提交与推送

将本次准备提交的实际变更整理为「类型前缀＋中文标题、空行、中文修改列表」，并按调用意图完成本地提交和远程推送。此 Skill 可跨项目使用，提交规则以当前仓库为准。

## 调用方式与授权范围

- 用户直接调用 `$git-commit-message` 且没有附加限制时，默认授权本次「确定范围 → 必要时暂存 → 生成信息 → commit → push」全流程。先简短说明拟提交范围及远程目标，再直接执行，不增加重复确认步骤。
- 用户明确要求「只生成」「预览」「不要提交」「不要推送」时，按其限制执行。自然语言仅要求生成、填写或总结提交信息时，只读生成；自动匹配到此 Skill 不等于用户授权 commit 或 push。
- 用户要求修改、完善或解释 Skill 本身时，以当前请求确定工作范围。提交和推送遵循当前仓库及用户明确指令。
- 用户指定文件、远程或分支时遵循指定范围；仅当范围或远程目标无法可靠确定时，询问缺少的信息，不重复索取已有授权。

## 确定变更范围

- 遵循当前仓库适用的 `AGENTS.md`，读取现有 commitlint 配置及近期提交标题，确定允许的类型和长度限制。已有规则足够时不要扩大配置排查范围。
- 先执行 `git status --short`，再读取相应的文件清单与完整 diff。使用 `git diff --cached --no-ext-diff --no-textconv` 查看暂存区，使用 `git diff --no-ext-diff --no-textconv` 查看未暂存的已跟踪文件变更。
- 用户明确指定文件、提交或比较范围时，以指定范围为准；否则只要暂存区有变更，就仅基于暂存区生成。存在部分暂存文件时，不把同文件中尚未暂存的内容写入提交信息。
- 用户指定的提交文件之外已有其他暂存内容时，不让这些内容混入本次提交，也不自行取消用户的暂存；无法在保留暂存状态与部分暂存边界的前提下隔离提交时，先澄清处理方式。
- 没有暂存变更时，通过 `git ls-files --others --exclude-standard` 获取未跟踪文件，检查本次工作区的已跟踪变更和相关未跟踪文本文件。只读模式基于这些内容生成草稿，在代码块外注明「根据工作区生成，尚未暂存」；全流程模式按核实过的本次文件路径执行 `git add -- <路径...>`，再基于实际暂存 diff 生成信息。不自动纳入忽略文件、已知无关修改或未检查的文件，不用笼统的 `git add -A` 扩大范围。
- 按文件核对所选范围的完整 diff，大文件分段读完，截断输出时继续读取。关键字搜索与统计用于定位，正文条目应有具体变更依据。二进制资源只根据可核实的路径、类型和变更状态描述。
- 没有变更时说明「当前没有可生成提交信息的变更」，不制造空提交，也不顺带推送历史提交；用户明确要求继续上次失败的推送或推送已有提交时，直接进入远程检查与推送。遇到未解决冲突或正在进行的 merge、rebase、cherry-pick 时停止自动提交，报告当前状态。

## 撰写规则

- 标题格式为 `<type>: <中文摘要>`，使用英文冒号和一个空格，默认不添加 scope；项目强制要求 scope 时按项目规则处理。
- 按实际目的选择类型，并遵守仓库允许值：`feat` 新功能、`fix` 修复、`docs` 文档、`style` 代码格式、`refactor` 重构、`perf` 性能优化、`test` 测试、`chore` 工具维护、`build` 构建、`revert` 回退。界面行为修改不能仅因涉及样式文件就归为 `style`。
- 标题概括主要问题或交付能力，必要时带上模块名，让读者看出改动范围。避免「修改代码」「更新内容」等空泛描述，细节放入正文。类型、长度、正文换行等均服从当前项目的提交校验规则。
- 标题后空一行，正文每项使用 `- ` 开头。优先说明行为、能力或维护方式的具体变化，文件名与实现细节仅在有助于理解时出现。例如「刷新订单列表时保留筛选条件」可以直接说明用户可感知的结果。
- 修改原因有明确依据且有助于理解时，将触发场景、解决的问题或设计原因融入对应条目。依据可来自用户需求、相关代码或已验证现象，无法确认时只描述可核实的变更。正文补充标题未包含的信息。
- 篇幅随业务意图的数量和复杂度调整。单一小改动通常用一至两条，跨文件实现同一能力时合并说明，多项能力按业务意图归并。每条保留独立信息，避免逐文件罗列或重复凑条数。
- 所有自然语言使用中文；代码标识符、路径、API、命令和产品名称保留原文。
- 以所选范围的最终净变更为依据，历史 commit 信息和聊天记录用于理解背景。逐条核对文案与当前 diff 的对应关系，已经撤回或被后续变更抵消的内容应从文案中删除。按最终结果组织内容，省去开发时间线、待办和后续计划，效果与验证结论只写有证据支持的部分。
- 正文聚焦修改内容。用户另有验证说明要求时，仅补充已执行且有结果依据的检查；不要默认追加测试、风险等模板章节。
- 存在多个独立主题时可在代码块外简短建议拆分，但仍按用户指定范围生成完整草稿，不自行拆分提交或调整暂存区。

## 输出格式

输出前核对主要变更是否覆盖、每条说明是否有当前 diff 依据，以及标题与正文是否存在冗余。只读模式输出一个 `text` 代码块，包含完整提交标题和正文。全流程模式完成后也展示该代码块，并简短报告提交短 SHA、远程与目标分支、推送结果。必要的范围或状态说明放在代码块外。下方示例展示格式与描述粒度，实际内容根据当前变更生成。

```text
fix: 修复订单列表刷新后丢失筛选条件的问题

- 刷新与分页请求沿用当前筛选条件，避免刷新后展示筛选范围外的订单
- 返回订单列表时恢复已选状态和关键词
```

## 提交与远程推送

只生成信息时，在输出后结束。仅本地提交时执行第 3 步并报告 SHA 和工作区状态。包含推送时按下列顺序执行，涉及远程状态的判断以本次成功 fetch 后的数据为准。

1. **提交前确定目标。** 获取当前分支；detached HEAD 下不自行创建分支或猜测目标。优先采用用户指定的远程与分支，否则采用当前分支配置的 upstream。没有 upstream 时，优先使用已配置的 `branch.<name>.pushRemote`、`remote.pushDefault`，其次使用唯一远程，再其次使用 `origin`，目标为当前同名分支；仍有歧义则询问。远程必须实际存在，不能把指向本地仓库的 upstream `.` 当作远程服务器。读取远程信息时不在回复中暴露 URL 中的凭证。
2. **核对待推送历史。** 通过针对目标的 fetch 检查远程分支和提交关系；新建远程分支时先确认目标分支确实不存在，不能把网络或认证失败当作不存在。当前分支落后或与目标分叉时停止，不自动 pull、merge、rebase 或覆盖远程历史。push 会包含该分支全部尚未推送的祖先提交：存在与本次任务无关且未获授权的历史提交时，先列明并澄清范围；本次任务内已授权的提交直接继续。
3. **生成并提交。** 核对暂存 diff 与提交说明一致；等待用户回复期间或其他工具可能改动了暂存区时重新读取。多行信息写入仓库外的临时文件，再通过 `git commit -F <文件路径>` 提交，保留真实换行并避免 shell 插值。运行项目要求的检查和既有 hook，不使用 `--no-verify`，不修改 hook 或全局 Git 配置。提交成功后记录实际 SHA，核实本次提交的文件范围。
4. **推送指定分支。** 核对当前分支和 HEAD 仍与刚才记录一致，再执行 `git push --no-follow-tags <remote> <完整 SHA>:refs/heads/<目标分支>`。没有 upstream 且采用同名分支策略时，在核对推送结果后为当前分支设置对应 upstream。推送前确认查询地址和推送地址指向同一仓库，且只有一个推送地址。
5. **报告实际结果。** 检查 push 退出状态，成功后通过 `git ls-remote --heads <remote> refs/heads/<目标分支>` 核对远程 SHA。远程 SHA 与所记录提交一致时报告已确认同步；push 成功但后续核对失败时区分报告，不声称已核实。最后查看工作区状态，说明仍有未提交变更时的范围。

## 失败与重试

- 暂存、检查或 commit 失败时停止后续推送，报告失败步骤与必要错误信息；不自动改写业务代码、撤销用户修改或绕过校验。
- commit 已成功、push 失败时保留本地提交，明确报告「本地已提交，远程推送失败」及 SHA。认证、权限、分支保护或非快进拒绝时停止，不无限重试，不强推，不自动创建 PR 替代目标。
- 用户要求重试推送时先核对已有提交和远程状态，再推送同一个提交；不重新 commit，不自动 amend。若网络中断导致上次结果不明确，先查询远程 SHA，已经同步则直接报告，尚未同步且提交关系允许时再重试一次。
