# 从参考项目提取开发规范

目标是形成可应用于其他项目的规则。先确定参考项目、拟采用的技术栈、提取主题及输出位置。用户只要求查看或比较时，在回复中给出候选规则和证据，应用修改遵循用户授权。已有项目接入或升级规则时，使用同工具包的 [project-bootstrap](../project-bootstrap/SKILL.md)。

## 取证与取舍

- 先读取参考项目的 `AGENTS.md`、工程规范和技术栈配置，再选择能验证对应约定的代表性代码与检查入口。有 CodeGraph 索引时优先通过 CodeGraph 定位实现。读取参考项目即可，工具声明、脚本内容和代码用来核对实践；检查是否运行要按实际结果单独报告。
- 把证据区分为**明文规则**、**实现惯例**和**待确认**。仓库中有少数实现只证明这些实现存在；遇到文档与代码冲突、各项目做法不同或用户选型不同，分别列出证据与适用边界。以已确认的选型形成候选规则，未决项保留供选择。
- 记录来源、可确认的 Git 提交、相对文件路径和提取日期。已修改的工作树标明观察了未提交内容，无 Git 的来源标明无法核对提交。授权公开的定位信息可随规范保存，其余来源和精确定位放在本地记录，公开材料只保留通用取舍与允许公开的归属。工具包的 `local/` 可保存本机来源记录。
- 将可复用做法写成可操作的要求、适用条件和验证方式。用自写的最小例子表达规则，排除业务逻辑、真实数据、凭证、私有路径和未获分发授权的原文。区分必选项、默认项与项目可选项。

## 交付

1. 指出哪些通用或技术栈文档需要新增或修改。先查看目标规范库现有规则，并去除跨文档重复和冲突。在本工具包维护规范时，先解析 Skill 的真实路径，再从工具包根目录读取 [规范入口](../../standards/README.md)。
2. 对每条重要提议给出短规则、适用范围和证据分级，列出仍需确认的冲突。维护者未选择的做法保留为差异或开放项。
3. 写入经授权的目标后，检查文档链接与引用示例。新技术栈若尚未接入生成器的选项，明确报告。规范库更新后，已有项目通过显式规则升级采用新版本。
